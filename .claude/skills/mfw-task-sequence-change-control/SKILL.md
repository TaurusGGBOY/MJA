# MFW 任务顺序与改动控制

## 目标

把“先逐个读取配置并说明任务，再集中实施改动”作为一个有状态的项目流程。这个 Skill 永远不运行真实游戏任务；它只读取当前项目配置和状态机定义来说明任务。说明阶段只读；改动阶段只在用户指定的时机开始。无论用户一次给出全部任务、给出几个任务，还是使用“下一个任务”逐项推进，都保持任务顺序和改动记录不丢失。

## 不可违反的契约

- 先冻结任务范围和顺序，再开始逐项说明；不能在过程中自行追加、删除或重排任务。
- 每次只说明当前任务；在 `catalog` 或多任务 `explicit` 范围内，当前任务完成说明、改动登记和唯一澄清回答后，自动按冻结顺序进入下一个任务，不要求用户额外说“下一个任务”。
- 用户提出任务改动时，先登记到改动账本，不立即编辑代码、资源或 workflow；登记完成后结束当前回合。
- 用户提出改动后，只提出一个澄清问题；用户回答后只记录回答，不继续追问、不提前解释技术方案、不提前修改。
- 只有在已经说明最后一个任务，或用户明确说“开始统一修改/执行改动”时，才实施账本中的改动。
- 这个 Skill 的任何阶段都禁止启动真实游戏、MFW、ADB 或 live acceptance；改动实施阶段只做离线检查。如需真实验收，等待用户另行授权并切换到相应运行 Skill。
- 不把 `Tasker.Task.Succeeded`、绿色 UI、点击记录或旧日志当作业务成功证据。实施后的验证必须使用离线测试、资源校验、diff 检查和新鲜结果；真实运行另遵循项目 MFW Skill 与 `AGENTS.md`。

## 会话状态

在对话中持续维护以下状态；会话很长或可能发生上下文压缩时，同时写入项目根目录的 `.mfw-task-sequence/` 会话记录，文件名使用日期和短标识。不要把未确认的猜测写成已完成改动。

| 字段 | 内容 |
| --- | --- |
| `scope_mode` | `explicit`（用户列出任务）或 `catalog`（用户说全部任务） |
| `task_list` | 冻结后的任务 ID、显示名、原始顺序、日期适用性 |
| `current_index` | 当前正在说明的任务位置，从 1 开始 |
| `described_tasks` | 已经向用户说明过的任务 |
| `change_ledger` | 按任务归属的待实施改动 |
| `phase` | `intake`、`walkthrough`、`change_recorded`、`ready_to_apply`、`applying`、`verification` 或 `done` |
| `stop_reason` | 本回合停止是因为等待“下一个”、等待更多改动，还是已完成统一修改 |

改动账本至少记录：任务 ID、用户原话的准确意图、期望行为、涉及的 workflow/资源/代码范围、证据或依据、优先级、状态（`pending`/`implemented`/`verified`/`blocked`）。用户没有明确要求的优化不得擅自加入账本。

## 建立任务清单

1. 先读取项目 `AGENTS.md`，使用 canonical 路径 `/Volumes/my_disk/project/MJA`。
2. 代码发现优先使用 codebase-memory MCP；不可用时再用 `rg`、`rg --files` 和定向文件阅读。
3. 以当前生效候选包的任务注册表、`interface.json`、任务配置、pipeline JSON 和 workflow definition 为任务清单来源，保持配置中的原始顺序；不要按文件名、字母或个人猜测排序。
4. 说明任务时以配置定义为唯一执行语义来源：沿着任务 `entry`、pipeline 节点、`recognition`、`action`、`next`、`on_error`、结果后置条件和边界节点读取完整路径。原始自然语言 workflow 只能作为差异对照，不能用来补充当前配置中不存在的步骤；配置路径不存在或内容不足时，明确标记未知，不要补写假步骤。
5. 用户说“所有任务”时，冻结当前项目目录中可识别的业务任务清单；日期限定任务要标注适用日期，不能静默丢弃。用户列出任务时只纳入用户明确列出的任务，规范化别名、去重并按项目原始顺序排列。
6. `GAME_START` 是 MFW 的共享启动前置步骤，默认单独标记为前置条件，不把它伪装成一个业务任务；除非用户明确要求，也不在逐项业务说明中重复展开。
7. 建立清单后先回复总数、范围、顺序和当前任务编号，然后只说明第一个任务。

## 单个任务的说明格式

对当前任务给出以下信息，避免只报任务名称；每一项都要能回指到配置文件或状态机定义：

- 任务 ID、显示名、在清单中的位置。
- 生效配置文件、任务入口、初始节点和前置边界。
- 按配置状态机的实际转移顺序列出步骤；对每一步区分识别条件、输入动作、等待结果、关闭/返回和失败分支。
- 配置中明确存在的条件分支：什么情况下点击、什么情况下跳过、什么情况下必须 fail closed；不要把“线程结束”写成业务成功。
- 配置定义的任务特定成功后置条件、结果状态和最终边界，例如奖励弹窗、资源状态、页面状态或回到主页。
- 当前配置与原始 workflow 的差异、已知风险和证据路径；没有配置证据时写“待验证”，不自行推断。
- 当前改动账本中属于该任务的条目。

说明阶段不得启动 MFW/ADB、点击游戏、改动候选包、修改截图或生成伪造结果。只进行只读代码、资源、配置和日志检查；不为了“确认步骤”而真实运行任务。

## 对话推进规则

### 首次请求

识别用户意图：

- 用户给出任务列表：使用该列表建立 `explicit` 清单。
- 用户说“所有任务”：从项目清单建立 `catalog` 清单，并标记日期限定任务。
- 用户只说“第一个任务”：先建立能从项目读取到的清单，再只说明第一个；不要趁机解释后续任务。

首次回复必须说明：`当前任务 1/N`、任务名、已冻结范围、说明阶段不会修改代码，以及用户可以说“下一个任务”或提出改动。

### 自动推进与“下一个任务”

在 `catalog` 或多任务 `explicit` 范围内，确认当前任务已经说明并登记其状态后，将 `current_index` 加 1，自动只说明下一个任务。用户不需要发送“下一个任务”；该短语仍可作为用户主动推进的兼容指令。不要因为当前任务没有改动就把整个清单一次性展开，也不要在推进时实施已有改动。

### 用户提出改动

把改动绑定到当前任务或用户明确指向的任务，原样记录意图；不要因为改动看起来简单就立即修改，也不要在用户回答澄清问题后自行扩展成新的技术要求。

- 若当前任务不是清单最后一个：写入 `change_ledger`，回复“已记录，尚未修改”，提出唯一澄清问题；用户回答后立即登记回答并进入下一个任务，不等待“下一个任务”指令。
- 收到一项任务改动后，只问一个与验收边界或期望行为有关的澄清问题；这个问题是本项改动唯一的问题机会。不要连续列出多个问题。
- 用户回答这个问题后，把回答原样作为该改动的 `clarification`/`user_explanation` 追加到账本；不继续追问、不执行技术分析、不修改代码、不运行游戏，也不因为回答内容自动推进到下一个任务。
- 若用户同时说“改动”和“下一个”：改动登记和唯一澄清问题优先；用户回答后照常自动推进，不把“下一个”当作额外前置条件。
- 若用户说“先记着”“后面改”：只登记，不编辑、不运行、不验证 live 状态。
- 如果改动目标不明确到会改变任务范围或业务语义，记录为 `blocked` 并只询问最小必要问题；不要用猜测替代确认。

### 到达最后一个任务

说明完最后一个任务后，将 `phase` 置为 `ready_to_apply`，先汇总任务清单和全部 `pending` 改动。若用户没有撤回或要求继续记录，按照用户的约定统一实施改动；不要只实施最后一个任务的改动而遗漏前面登记的条目。

如果用户明确说“开始统一修改”“执行这些改动”或等价指令，即使清单尚未走到最后，也可以进入实施阶段，但要在实施前列出尚未说明的任务并确认不会误改其范围；没有这种明确指令时，必须继续停在说明阶段。

## 统一实施规则

1. 先复核账本：逐条映射到当前配置、pipeline、识别器、动作和结果后置条件；同时保留用户最初的改动要求与澄清回答，发现互相冲突时暂停并报告冲突。
2. 先按 `systematic-debugging` 查明根因，再修改；不得用加重试、盲点坐标、放宽 OCR 或伪造 success 掩盖未确认的问题。
3. 修改只覆盖账本授权范围，使用 `apply_patch`；保留用户已有改动，不做“顺手重构”。
4. 涉及多个正式 MFW 业务任务时，遵循 `AGENTS.md` 的 worktree、候选构建和证据约束；本 Skill 仍然禁止真实模拟器操作。
5. 实施后只执行相关离线测试、资源/pipeline 校验、`git diff --check` 和必要的结果契约静态检查；验证失败就停在 `blocked`，不能报告已完成。
6. 最终汇报列出：实际改动文件、每条改动对应的任务、用户原始要求与澄清回答、离线验证结果、未解决风险和“未运行真实游戏”。汇报后结束当前回合。

## 停止条件

- 单任务范围且用户尚未要求继续：任务说明完成后停止并等待。
- 多任务或 `catalog` 范围：当前任务完成后自动进入下一个；只有等待用户回答唯一澄清问题、遇到冲突或到达最后一个任务时停止。
- 改动已登记但当前任务不是最后一个：停止，不修改。
- 账本存在冲突、证据不足或需要扩大用户授权：停止并报告阻塞点。
- 所有任务说明完成且改动已统一实施并通过离线验证：停止，不自动开始下一轮 MFW。
